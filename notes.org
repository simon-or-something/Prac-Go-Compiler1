= Prompt:
I am designing a compiler in go. What is the intended way to design the interface between driver -> lexer -> parser -> sema -> codegen?

In java you would write a class
In C you would have either a struct or a global variable
In python you would have a dynamic list passed into functions
In javascript you do whatever you like

What is the idiosyncratic design premise of go?
= Response (i only care about this part):
Go's answer is: the package is the class, the exported function is the constructor-plus-method, and the state lives in an unexported struct that nobody outside can see. Data between phases is dumb — plain structs with exported fields and no behavior.
#+END_EXPORT
this is surprisingly nice tbh. that's like in C but with higher level, in C you'd have a header with the individual functions and a TU global variable if you want mock-encapsulation
Here you have encapsulation at a language level
